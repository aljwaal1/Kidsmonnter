# KidsMonnter — سجل التقدم 04

## النطاق

تم العمل على نموذج تشخيص خدمة الحماية فقط. لم يتم تغيير منطق العدّاد، شاشة القفل، الصلاحيات، Manifest، أو طريقة حفظ بيانات المستخدم في هذا التشغيل.

## ما تمت مراجعته

- الحقول التي يرسلها Android Native عبر `getStatus`، وبالأخص `serviceHeartbeatMs` و`overlayAllowed`.
- طريقة تسجيل نبض الخدمة داخل `MonitorService`.
- نافذة اعتبار نبض الخدمة حديثًا.
- اختبارات التشخيص الموجودة قبل التعديل.

## المشكلة

كان النموذج يحدد صحة خدمة الخلفية فقط، لكنه لا يعطي نتيجة واحدة توضّح هل الحماية جاهزة فعليًا. قد تكون الخدمة سليمة بينما صلاحية Overlay ناقصة، أو تكون الصلاحية موجودة بينما الخدمة متوقفة.

## التغيير المنفذ

تمت إضافة تصنيف `GuardReadiness` بالحالات التالية:

- `disabled`: الحماية غير مفعلة.
- `starting`: الحماية مفعلة ولم تصل أول نبضة بعد.
- `ready`: الخدمة سليمة وصلاحية Overlay موجودة.
- `overlayMissing`: الخدمة سليمة لكن شاشة القفل لا تستطيع الظهور.
- `serviceStale`: آخر نبضة أقدم من النافذة المسموحة.

أضيفت كذلك الدالة `isReadyAt` لتقديم نتيجة منطقية موحدة يمكن للواجهة الاعتماد عليها لاحقًا.

## الاختبارات

تم توسيع `test/guard_diagnostics_test.dart` لتغطية:

- توقف الحماية.
- انتظار أول نبضة.
- الجاهزية الكاملة.
- نقص Overlay مع خدمة سليمة.
- توقف الخدمة مع نقص Overlay لضمان أولوية تشخيص الخدمة.
- نبضة مستقبلية بسبب اختلاف الساعة.
- حد 15 ثانية بدقة، ثم أول ميلي ثانية بعده.

## ما بقي

1. ربط `serviceHeartbeatMs` بنموذج `GuardStatus` في الواجهة.
2. عرض بطاقة تشخيص مرئية للمستخدم.
3. عرض وقت آخر نبضة بصيغة مفهومة.
4. إضافة إجراء واضح عند توقف الخدمة، مثل إعادة تشغيل الحماية أو فتح إعدادات البطارية.
5. اختبار السلوك على أجهزة Android من شركات مختلفة.

## قرار السلامة

تم إبقاء هذا التغيير مستقلًا وقابلًا للاختبار قبل ربطه بالواجهة، لتجنب إظهار حالة خاطئة للمستخدم أو التأثير على منطق القفل الحالي.
